# DeepSeek Harness 企业 Agent 工作平台预研

调研日期：2026-08-14

## 背景与结论

DeepSeek Harness 已经将模型适配器、工具、会话日志、agent loop（智能体循环）、客户端 UI、subagent 和工作流组合为插件，但已发布产品仍面向个人并以单机为范围。企业目前还不能让员工登录后直接获得已分配的模型和插件而无需管理模型提供方 API 密钥，也不能在另一台设备上恢复工作、向项目共享选定会话，或通过统一管理服务治理 Agent Team。

让所有员工共用一个多用户 Harness 进程，会把本地代码仓库、进程、凭据和故障域集中到一台机器。让每台员工设备运行一个 Harness Runtime，可以保留本地编码体验和执行位置，但会产生企业级身份、策略、分发、用量、复制、授权和审计职责，而任何单个本地 Runtime 都无法拥有这些职责。

产品流程尚不足以冻结一套完整协作模式。平台需要稳定的企业基础能力，同时让私有与共享的默认值、交接操作、评论、工作区转移和多 agent 协作继续作为可替换实验。

本预研的结论是：产品应采用“员工本地 Harness Runtime + 企业控制面 + 模型网关 + 数据服务 + 插件生态”的形态。第一阶段先完成企业登录、受管模型访问、Token 与成本配额、插件分发和基础审计；后续再基于同一套身份、项目、策略和事件数据扩展会话恢复、共享会话、项目协作与 Agent Team。

## 产品形态

建设一个由员工本地 Harness Runtime 和集中式企业控制面组成的企业 Agent 工作平台。本地 Runtime 仍是访问员工机器并执行工作的权威。控制面拥有组织身份、有效策略、模型访问、配额、受管插件分发、项目成员关系、复制数据和审计。后续可增加企业 Runner，用于执行必须脱离员工设备持续运行的长期或共享工作负载。

员工应用通过插件和已声明 slot 扩展现有客户端，不维护长期 UI fork。管理员控制台是独立的服务端 Web 应用，因为它管理组织级状态，而非某个本地 Runtime。客户端和 Host 插件把员工应用连接到管理员控制台使用的同一套企业 API。

Harness 插件继续拥有编码、办公和行业具体功能。企业平台只拥有必须一致作用于所有插件的设施：身份、策略、分发、模型路由、数据保留、授权、复制、计量和审计。

### 系统职责

| 组件 | 职责 |
|---|---|
| 员工 Runtime | 本地 agent 执行、工作区访问、本地会话持久化、策略消费、后台复制和员工 UI |
| 企业控制面 | 组织目录、项目、角色、有效策略、模型目录、配额、受管插件目录、设备记录、保留策略和审计查询 |
| 模型网关 | 用户与项目授权、模型提供方凭据托管、请求限制、用量结算、上游路由和模型审计 |
| 复制服务 | 会话事件与附件增量复制、恢复、可见性元数据、单写者租约和保留策略执行 |
| 企业 Runner | 可选的远程执行环境，用于不能依赖员工设备的长期任务、共享自动化和 Agent Team |

本地集成应通过一个企业组合包交付，其中包含可独立替换的客户端和 Host 插件。服务端实现可以模块化，但 Harness 插件机制不能取代多用户数据库、身份提供方集成、模型网关或管理服务。

### 企业身份与受管模型访问

控制面直接接入 LDAP 或 Active Directory，或者通过企业身份提供方接入。桌面应用通过 OIDC/OAuth 的 Authorization Code with PKCE 或设备流程完成认证，绝不保存 LDAP 密码。登录成功后获得短期用户会话、设备身份、组织与项目声明，以及带 revision 的有效策略。

管理员按用户、用户组和项目分配模型路由。一次分配可以指定提供方路由、精确模型、默认推理强度、最大输出、并发数、每分钟请求数、每分钟 Token、每日或每月 Token 预算、金额预算和降级策略。员工模型选择器只列出有效分配，但模型网关会重复每项授权检查，因为本地可见性不是安全控制。

员工永远不会收到上游模型提供方 API 密钥。模型配置只携带凭据引用，与现有[凭据所有权](https://github.com/deepseek-ai/deepseek-harness/blob/99f6f02fecdb7dff40c3fbc9470f5907c29f74ca/.agents/notes/implemented/architecture/2026-07-30-credential-boundaries-and-atomic-registration.md)保持一致。网关从企业密钥存储或 KMS 解析模型提供方凭据，并使用短期企业令牌认证员工。请求在发出前预留其允许的最大用量，完成后结算模型提供方报告的输入、输出、缓存和推理用量，并释放未使用的预留额度。失败和取消调用同样保留明确的计量结果。

除非设备也受管，否则企业策略只能治理企业提供的模型路由。阻止用户安装不可信适配器、提供个人密钥或调用外部端点，还需要受管 profile、插件允许列表、端点策略，以及必要时的操作系统或网络控制。

### 受管插件分发与 UI 扩展

企业控制面发布经过签名的已批准组合包、插件、skill、agent preset 目录，并携带版本锁定、灰度用户组、兼容性要求和回滚目标。员工 Runtime 在激活前验证签名和策略，上报当前启用清单，并保留上一个已批准版本用于恢复。企业策略区分必需、允许和禁止的扩展；用户 patch 不能禁用必需的安全或路由插件。

现有客户端已经通过 [Client 插件加载模型](https://github.com/deepseek-ai/deepseek-harness/blob/99f6f02fecdb7dff40c3fbc9470f5907c29f74ca/.agents/notes/implemented/architecture/2026-07-23-client-plugin-loading-model.md)描述的 slot 系统组合 UI。企业插件可以增加登录与账号状态、受管模型展示、项目与共享会话导航、设置区、审计提示和 Agent Team 状态。如果缺少通用扩展点，应在其 slot owner 中补充，并在可行时贡献给上游，而不是替换整个外壳。

模型动态编写的插件不会自动成为企业批准的软件包。它们的执行信任、进程生命周期和审批语义与签名管理分发保持分离。只有经过明确的评审和发布操作，动态插件才能进入受管目录。

### 会话复制、恢复与审计

仅追加的 Session Event 日志继续按照[事件溯源会话决策](https://github.com/deepseek-ai/deepseek-harness/blob/99f6f02fecdb7dff40c3fbc9470f5907c29f74ca/.agents/notes/implemented/architecture/2026-06-11-event-sourced-sessions.md)作为模型可见历史的真源。本地 `SessionPersistence` 继续在不引入网络延迟的情况下写入。独立的 `SessionReplication` 能力族将已提交事件后缀和附件异步复制到企业服务；模型请求和本地持久化不会等待普通复制确认。

复制协议标识每个会话、设备、格式版本和连续事件位置。上传具有幂等性，拒绝分叉前缀，并从已确认位置继续。附件和产物使用内容身份、加密、受限传输和保留元数据，不在事件批次中反复嵌入。设备恢复会下载经过授权的会话，校验其格式和完整事件前缀，通过本地持久化提供方完成物化，并记录执行恢复的设备和策略 revision。

复制会话并不意味着另一台设备拥有相同工作目录。协作编码会话还要记录可移植的项目引用，例如仓库身份、revision、分支、未提交 diff 和产物。恢复或交接需要明确重建 worktree，而不是镜像员工机器上的任意文件。

审计数据和协作数据是建立在持久事实上的独立投影。审计记录标识操作者、设备、项目、操作、模型路由、策略 revision、插件清单、用量和结果。提示词、工具输出、附件和代码内容遵循明确的组织策略，因为元数据保留与内容保留具有不同的法律和隐私后果。模型提供方密钥和解析后的凭据绝不进入任何记录。

### 项目共享会话

每个会话具有私有、项目或组织等可见性策略，企业服务基于项目成员和角色执行检查。初始产品默认新会话为私有，并要求显式共享；部署可在验证员工预期后覆盖该策略。

共享会话初期支持授权后的只读查看、实时事件观察、导出和基于 fork 的继续工作。一台设备持有活动会话的追加租约。其他成员可以从一个已完成事件位置 fork，或者在后续接管流程中，等待原写入者释放租约，或由授权管理员处理遗留租约后获得租约。第一版不会把并发事件后缀合并进同一会话。

评论、评审和项目批注保持在模型历史之外，除非用户明确将其提交给 agent。这样可以防止社会化协作数据静默改变后续模型请求，同时保留归属和审计。共享会话不会扩大仓库、工具、凭据或模型权限；每个查看者或 fork 都依据该成员的有效策略重新解析授权。

### Agent Team

现有 [subagent 能力](https://github.com/deepseek-ai/deepseek-harness/blob/99f6f02fecdb7dff40c3fbc9470f5907c29f74ca/.agents/notes/implemented/feature/2026-06-21-subagent-capability-seam.md)、[动态工作流引擎](https://github.com/deepseek-ai/deepseek-harness/blob/99f6f02fecdb7dff40c3fbc9470f5907c29f74ca/.agents/notes/implemented/feature/2026-07-05-dynamic-workflows.md)和[按会话设置的 agent preset](https://github.com/deepseek-ai/deepseek-harness/blob/99f6f02fecdb7dff40c3fbc9470f5907c29f74ca/.agents/notes/implemented/architecture/2026-08-03-per-session-agent-presets.md)已经提供 Agent Team 所需的本地执行原语。企业层增加可复用团队模板、项目分配、汇总预算、持久调度、共享状态，以及由企业 Runner 支撑的远程提供方。

团队模板定义协调者、编码、测试、评审或研究等角色，并为每个角色分配 preset、模型路由、工具集、数据范围、并发限制、时间限制和 Token 或成本预算。子 agent 的授权是发起用户、项目、父 agent、团队模板和执行环境权限的交集；委派绝不授予更大权限。团队用量计入完整后代树，因此创建子 agent 不能绕过用户或项目配额。

Agent Team 分三个产品阶段演进：单个员工会话内的临时本地团队、子会话与任务可跨重启延续的持久项目团队，以及由企业 Runner 调度的分布式团队。私有仓库操作优先使用本地 worker；远程 worker 需要显式的仓库或产物传输，以及经过认证的远程 subagent 实现。

### 交付阶段

1. **受管模型访问：** 企业登录、组织目录与用户组映射、模型网关、模型分配、Token 与成本配额、签名插件分发、活动清单上报和基础审计。
2. **连续性：** 异步 Session 复制、附件传输、保留策略、设备恢复和管理员诊断，不引入共享写入。
3. **项目协作：** 项目成员关系、私有/项目可见性、只读共享会话、实时观察、fork 交接和可移植代码变更引用。
4. **Agent Team：** 团队模板、后代预算、项目任务状态、企业 Runner 和经过认证的远程提供方。

每个阶段都形成可独立使用的产品闭环，并且不依赖尚未验证的办公功能。第一阶段中，员工登录后即可使用已分配模型，无需输入模型提供方密钥。后续阶段复用同一套身份、项目、策略和事件权威。

### 待验证的产品假设

- 项目会话应默认私有还是共享。
- 用户最重视只读观察、评论、fork 交接还是执行接管。
- 交接所需的代码状态是只有 diff、仓库 revision 加 diff，还是更完整的工作区快照。
- 登录令牌过期或管理员撤销权限后，离线模型访问和缓存企业策略应继续有效多久。
- 项目级、个人级还是成本中心级预算更容易产生明确行为。
- 哪些 Agent Team 角色和人工审批点能够改善结果，而不是增加协调成本。

平台记录采用、共享、重新打开、fork、交接、配额和失败信号，默认不把原始内容作为分析数据。产品行为保留在可替换插件中，而身份、授权、持久事件和计量保持稳定所有权。

### 公开生态证据

针对 `@deepseek-ai/dsh` `0.1.0-rc.6` 生态的 2026-08-14 公开 GitHub 和 npm 调研，没有发现能够完整实现跨设备 Session Event 复制、附件传输、恢复、冲突控制和企业授权的可安装插件。该结论覆盖公开可检索仓库和软件包，不代表私人实现一定不存在。

相邻项目解决的是更窄的问题：[dsh-memory-evolve](https://github.com/csyangwen/dsh-memory-evolve) 通过 Git 同步项目记忆、日志和待办；[dsh-interconnect](https://github.com/Chinesezjc/dsh-interconnect) 在实例之间转交消息和事件；[dsh-turn-rewind](https://github.com/Anionex/dsh-turn-rewind) 提供本地变更检查点和会话 fork；[dsh-share](https://github.com/hellodigua/dsh-share) 导出一轮对话用于分享。它们都不拥有本提案所需的完整企业复制与恢复语义，但其同步体验、实例间传输、本地检查点和展示模式仍可为独立提供方或 UI 插件提供参考。

### 与现有 Harness 能力的关系

本方案组合现有能力，而不改变它们的职责。事件溯源会话和 Session Persistence 继续拥有本地持久历史；用户设置和凭据引用继续拥有个人配置与机密解析；Client 插件加载和 slot 继续拥有 GUI 组合；preset、subagent 和工作流继续拥有按 agent 的组合与编排。`SessionReplication`、企业策略和受管分发是需要新增的职责。

## 关键取舍

**让所有员工运行在一个集中式多用户 Runtime 中。**这样可以简化服务端数据访问，但也会集中本地代码仓库、进程树、凭据、资源竞争和故障。需要中央持久性的工作负载使用可选企业 Runner；普通员工工作仍保持每台设备一个 Runtime。

**把模型提供方 API 密钥分发到员工设备。**这样可以简化直接适配器，但无法可靠撤销、执行配额和托管机密。模型网关保留模型提供方凭据，员工只获得短期企业登录令牌。

**把远程存储实现为唯一的 `SessionPersistence` 提供方。**这样会让网络进入本地追加和恢复路径。独立复制既保留离线工作和现有同步事件/后台写入设计，也让企业副本异步收敛。

**允许多台设备追加到一个共享会话。**多写者排序会影响模型历史、工具效果、代码状态和审计。在证据证明需要合并语义之前，单一追加租约加只读观察、fork 和显式接管可以提供确定性历史。

**把官方员工 UI fork 为独立企业前端。**fork 可以不受限制地控制布局，但需要持续承担上游修复和扩展变化。默认使用 Client 插件和 slot；管理员控制台由于数据和使用者本就不同而独立存在。

**把编码和办公功能构建进企业核心。**这样会让平台与每个插件竞争，并把治理发布绑定到产品实验。社区和企业插件拥有具体工作流；平台拥有共享管理设施。

**把相邻社区插件当作完整同步产品。**这些插件提供了有用组件，但没有共同定义 Session Event 身份、附件、恢复、租约、格式迁移、项目授权和审计。复用发生在特定提供方或 UI，而不是依赖隐式的跨插件协议。

## 目标状态

- 员工可以安装企业发行版、使用企业账号认证，并立即调用已分配模型，而无需输入或接收模型提供方 API 密钥。
- 模型网关独立于本地 UI 执行用户、用户组、项目、模型、并发、速率、Token 和成本策略，每个接受或拒绝的请求都会生成用量和审计结果。
- 管理员可以发布、分配、锁定、撤销和回滚经过签名的组合包、插件、skill 和 preset；员工 Runtime 验证策略并上报当前启用清单。
- 在普通控制面或复制服务故障期间，本地 agent 工作和 Session Persistence 仍按明确的缓存策略与令牌过期规则可用。
- 经过授权的替换设备可以恢复已复制会话及附件，不接受分叉或不支持的事件日志；每次恢复都可以归因并接受审计。
- 项目成员可以发现经过授权的共享会话、只读观察并从已完成位置 fork，而不会获得源用户的模型、仓库、工具或凭据权限。
- 一个活动会话只允许一个追加写入者；租约释放、过期、管理员恢复和接管在同会话继续功能发布前具有明确的持久和审计结果。
- 协作编码交接会标识重建工作所需的仓库状态和变更，而不是假设本地路径指向共享文件。
- Agent Team 模板限制每个角色的模型、工具、数据、并发、时间和预算；后代权限不能超过发起用户和项目的授权，汇总用量包含每个子 agent。
- 每个用户可见阶段都有聚焦包测试、组装后的无密钥快照、相关浏览器覆盖、文档、所有持久或线格式的迁移处理，以及运行诊断。

## 风险

- Harness 尚未正式发布，因此 Client slot、会话格式和配置 API 可能变化。企业发行版必须锁定兼容版本，并把适配控制在少量插件中，不能让上游假设散布到控制面。
- 本地 Runtime 具有员工的操作系统权限。对于不受管设备，Harness 策略本身无法阻止有意用户读取本地数据、安装其他软件或绕过企业模型通道。
- 会话事件、工具输出、附件、diff 和提示词可能包含机密或受监管数据。在广泛复制之前，需要明确加密、脱敏、数据驻留、保留、删除、法律保留、导出和管理员访问策略。
- 异步复制会引入设备丢失、陈旧租约、分叉前缀、不完整附件和格式版本转换。服务必须在遇到分叉时快速失败，同时不能阻塞健康的本地持久化。
- 不同模型提供方 API 和流式失败的用量计量存在差异。预留和结算需要按提供方归一化，同时保留原始报告类别用于审计。
- 中央身份和模型网关会成为受管模型调用的可用性依赖。离线行为和缓存策略必须明确，不能意外回退到个人凭据。
- 签名分发使企业目录成为软件供应链权威。发布者身份、评审、来源证明、回滚、泄露响应和设备清单是安全要求，而不只是管理便利。
- 产品协作假设可能错误。独立交付各阶段并衡量实际共享、fork、交接和 Agent Team 使用，可以限制替换失败工作流的成本。
- 远程 Agent Team 会增加调度、仓库传输、取消、所有权和遗留任务恢复问题。只有在本地团队和共享会话建立所需语义后，才应发布企业 Runner。
